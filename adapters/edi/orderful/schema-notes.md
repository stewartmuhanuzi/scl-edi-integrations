# Orderful Outbound Transaction Schema — 856 & 810

Discovered by POSTing incrementally-filled payloads to `POST /v3/transactions`
and reading Orderful's schema validation errors (same technique used earlier
to nail down ApparelMagic's auth). Each `unprocessableEntity` error names the
exact missing/extra field, so this is **live-validated against the real
schema**, not guessed from docs (Orderful's own reference pages for 856/810
don't publish a full JSON example).

Several real TEST transactions were created during discovery (856:
`991771780`, `991776105`, `991792891`, `991794170`; 810: `991790177`,
`991791032`, `991791734`, `991792581`, `991794170`). All harmless — TEST
stream, demo partner, no cleanup needed.

**Status: schema fully mapped for both.** Every segment used in
`build856.js`/`build810.js` is ✅ live-confirmed. Remaining `INVALID`
`validationStatus` on test transactions is a **guideline-level** concern
(retailer-specific implementation guides layer requirements on top of the
base X12 standard), not a schema gap — not worth chasing against Orderful's
generic default guideline; revisit once mapping to a specific real retailer.

## Top level (both 856 and 810)

```json
{
  "stream": "TEST",
  "type": { "name": "856_SHIP_NOTICE_MANIFEST" },   // or "810_INVOICE"
  "sender": { "isaId": "..." },
  "receiver": { "isaId": "..." },
  "message": { "transactionSets": [ { ... } ] }
}
```
`transactionSetTrailer` is **auto-generated by Orderful** — never send it.

## 856 (Ship Notice / ASN) — fully confirmed

```json
{
  "transactionSetHeader": [
    { "transactionSetIdentifierCode": "856", "transactionSetControlNumber": "0001" }
  ],
  "beginningSegmentForShipNotice": [
    {
      "transactionSetPurposeCode": "00",
      "shipmentIdentification": "SHIP0001",
      "date": "20260727",
      "time": "1200",
      "hierarchicalStructureCode": "0001"
    }
  ],
  "HL_loop": [
    {
      "hierarchicalLevel": [{ "hierarchicalLevelCode": "S" }],
      "N1_loop": [ { "partyIdentification": [{ "entityIdentifierCode": "ST", "name": "...", "identificationCodeQualifier": "92", "identificationCode": "..." }] } ],
      "carrierDetailsRoutingSequenceTransitTime": [{ "routing": "2" }],
      "dateTimeReference": [{ "dateTimeQualifier": "011", "date": "20260727" }]
    },
    {
      "hierarchicalLevel": [{ "hierarchicalLevelCode": "O" }],
      "referenceInformation": [{ "referenceIdentificationQualifier": "IA", "referenceIdentification": "PO12345" }]
    },
    {
      "hierarchicalLevel": [{ "hierarchicalLevelCode": "P" }],
      "marksAndNumbersInformation": [{ "marksAndNumbersQualifier": "GM", "marksAndNumbers": "00123456700300000229" }]
    },
    {
      "hierarchicalLevel": [{ "hierarchicalLevelCode": "I" }],
      "itemIdentification": [{ "productServiceIDQualifier": "VN", "productServiceID": "..." }],
      "itemDetailShipment": [{ "numberOfUnitsShipped": "5", "unitOrBasisForMeasurementCode": "EA" }]
    }
  ]
}
```

Key findings:
- `HL_loop` is a **flat array**, hierarchy inferred from order (S → O → P → I
  per carton/item), not from explicit parent-id fields — tried an explicit
  `hierarchicalIdNumber` and nested `HL_loop`-in-`HL_loop`; both rejected.
- Segment names are **reused across transaction types** — `N1_loop`,
  `carrierDetailsRoutingSequenceTransitTime` (TD5), `dateTimeReference` (DTM),
  and `referenceInformation` (REF) are identical to the 850's vocabulary and
  slot straight into an `HL_loop` entry.
- `marksAndNumbersInformation` (MAN — carton/SSCC marks), `itemIdentification`
  (LIN), and `itemDetailShipment` (SN1) are 856-specific wrapper keys, all
  confirmed with their field sets.
- `CTT_loop` is **not valid** for 856 (correct — 856 doesn't use CTT in X12).

## 810 (Invoice) — fully confirmed

```json
{
  "transactionSetHeader": [
    { "transactionSetIdentifierCode": "810", "transactionSetControlNumber": "0001" }
  ],
  "beginningSegmentForInvoice": [
    { "transactionSetPurposeCode": "00", "invoiceNumber": "INV0001", "date": "20260727" }
  ],
  "N1_loop": [
    { "partyIdentification": [{ "entityIdentifierCode": "ST", "name": "...", "identificationCodeQualifier": "92", "identificationCode": "..." }] },
    { "partyIdentification": [{ "entityIdentifierCode": "BT", "identificationCodeQualifier": "92", "identificationCode": "..." }] }
  ],
  "IT1_loop": [
    {
      "baselineItemDataInvoice": [
        {
          "assignedIdentification": "1",
          "quantityInvoiced": "5",
          "unitOrBasisForMeasurementCode": "EA",
          "unitPrice": "19.99",
          "productServiceIDQualifier": "SK",
          "productServiceID": "1017"
        }
      ]
    }
  ],
  "totalMonetaryValueSummary": [{ "amount": "99.95" }]
}
```

Key findings:
- `N1_loop` is **flat** at the top of `transactionSets[]` — no HL hierarchy
  for 810 (unlike 856).
- `IT1_loop` wraps its fields in `baselineItemDataInvoice` — close to, but
  distinct from, the 850's `baselineItemData` (that exact name is rejected on
  810). Field name is `quantityInvoiced`, not `quantity` (also rejected).
- `totalMonetaryValueSummary` field is `amount` (not `totalInvoiceAmount`,
  which was tried and rejected).
- `CTT_loop` is **also not valid** for 810 in Orderful's schema (tried and
  rejected) — somewhat surprising vs. raw X12 810 which does use CTT, but
  Orderful's JSON abstraction apparently doesn't expose it as a separate key.

## What's implemented

`lib/build856.js` and `lib/build810.js` use every segment above.
Genuinely open items are now about **content correctness for a specific
retailer** (their implementation guide may require additional segments,
different qualifiers, etc.), not about the base schema — that's normal and
expected; revisit once mapping to a real retailer's guideline.
